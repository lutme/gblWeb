# 性能

GBL 的热路径经过系统性优化。本章说明**做了什么、为什么**，以及如何自己跑基准。

## 启动期预计算：请求期零判断

注册只是排队；`Run()` 时的 `generateRoute` 一次性完成所有重活：

| 预计算项 | 请求期省掉的工作 |
|---|---|
| 每个参数的绑定类别（注入/文件/业务） | 不再逐请求做反射类型分类与接口满足探测 |
| 结构体参数的可导出字段列表（索引+名字+类型） | 不再逐请求做字段内省与 CanSet 检查 |
| `needsParse` 标志 | 不绑定任何业务值的 handler 完全跳过 body/query 解析 |
| 返回值 Content-Type | 不再逐请求判断序列化格式 |
| 参数名（源码 AST → 二进制 DWARF 两级恢复） | 每份源码只走一遍语法树：一次收集全部函数的行号区间建索引，handler 按索引解析；生产路径直接读二进制自带的 DWARF |
| 中间件链（全局+分组+终端） | 每条路由冻结一个切片，请求期直接复用 |

## 对象池：复用一切可复用的

| 池 | 复用对象 |
|---|---|
| `contextPool` | Context（请求结束清空全部引用再归还） |
| `keysPool` | `Context.Set/Get` 的 key/value map（清空后归还，消除 Set/Get 分配） |
| `responseWriterPool` | 响应写入器包装（归还前断开底层 writer 引用） |
| `pathParamsPool` | 路径参数 map |
| `paramsPool` | 反射调用参数切片（存指针避免装箱） |
| `bodyBufferPool` | JSON body 读取缓冲（绑定完成即归还，解码结果是独立拷贝） |
| `segmentPool` | 路由匹配的路径段切片 |
| `colorBufPool` | 控制台着色行缓冲 |
| `responseBufferPool` | 响应写出缓冲（序列化结果先落缓冲再写出） |

池化不仅省分配，还省 GC 压力——高并发下尤其明显。所有池对象归还前都清空引用，不会把上一个请求的数据钉在内存里，也不会泄漏到下一个请求。

## 请求期解析：每份数据只碰一次

- URL query 每个请求只解析一次——urlencoded body 解码不再顺带重复解析 query；
- JSON「body 是否为空」的判定合并进参数解析步骤，绑定阶段不做第二次 body 扫描；
- 压缩中间件的输出缓冲复用 `responseBufferPool`，压缩响应零新增分配。

## 路由匹配：热路径零分配

- 路径分段用 `strings.Cut` 切出**子串**，与原路径共享底层存储，不拷贝；
- 段切片来自池，预热后匹配过程不产生新分配；
- 无路径参数的静态路由不进基数树——按动词存进 map，匹配 O(1) 直查；只有带参数的动态路由走树；
- 树内静态子节点是 map 直查，变量分支才回溯。

## 惰性装箱

handler 的原始返回值以 `reflect.Value` 暂存；只有中间件真正调 `c.Result()` 时才装箱成 `any` 并缓存。不读 Result 的请求（绝大多数）零装箱分配。

## 诚实的取舍

与成熟框架的剩余差距来自**反射调用任意 handler 签名**的固有代价——这是"签名即 API"这一核心特性带来的取舍，不是轻易能抹平的。GBL 的策略是：把反射之外的一切开销压到最低（预计算 + 池化 + 零分配匹配），让反射成为唯一的主要成本。

如果你的场景对极限吞吐敏感且签名固定，结构体装配 + 简单中间件链是最快的组合；避免在热路径中间件里读 `Result()`（会触发布箱）。

## 自己跑基准

仓库内置进程内微基准（只导入标准库，主模块保持零依赖）：

```bash
go test -bench=. -benchmem -run=^$
```

工作负载：

| 基准 | 场景 |
|---|---|
| `BenchmarkGblStatic` | 无参数静态返回 |
| `BenchmarkGblPathParam` | 路径参数绑定 |
| `BenchmarkGblJSON` | JSON body 结构体装配 + 返回 |
| `BenchmarkGblMiddleware` | 两层中间件链 |

每个都有 `Parallel` 变体（共享引擎、GOMAXPROCS 并发）——这正是对象池在高负载下发挥作用的地方。与 gin 的对照基准在独立的 `ginbench` 模块里，使用相同 harness 与工作负载，数字可直接比较。

> 本站不展示具体基准数字：性能数字依赖硬件与 Go 版本，请以你本地 `go test -bench` 的结果为准。
