# 性能

GBL 的热路径经过系统性优化。本章说明**做了什么、为什么**，以及如何在自己的项目中做可信的基准对比。

## 启动期预计算

注册只是排队；`Run()` 时的 `generateRoute` 一次性完成重活：

| 预计算项 | 请求期省掉的工作 |
|---|---|
| 每个参数的绑定类别（注入/SSE/文件/业务） | 不再逐请求做反射类型分类与接口满足探测 |
| 结构体参数的可导出字段列表（索引+名字+类型） | 不再逐请求做字段内省与 CanSet 检查 |
| `needsParse` 与精确 query key 列表 | 没有业务参数和文件参数的 handler 跳过解析；多 key query 只解码可绑定名称 |
| 返回值临时 Content-Type | 提前设置，Flush 前无需猜测；运行时仍可在未提交时修正类型 |
| 参数名（源码 AST → 二进制 DWARF 两级恢复） | 只在 `needsNames` 时执行；自描述结构体不需要恢复形参名 |
| 中间件链（全局+分组+终端） | 每条路由冻结一个切片，请求期直接复用 |

## 对象池

| 池 | 复用对象 |
|---|---|
| `contextPool` | Context（请求结束清空全部引用再归还） |
| `keysPool` | `Context.Set/Get` 的 key/value map |
| `responseWriterPool` | 响应写入器包装 |
| `pathParamsPool` | 动态路由的路径参数 map |
| `paramsPool` | 反射调用参数切片 |
| `bodyBufferPool` | JSON 与 urlencoded body 读取缓冲 |
| `segmentPool` | 路由匹配的路径段切片 |
| `colorBufPool` | 控制台着色行缓冲 |
| `responseBufferPool` | 返回值、SSE 与压缩输出缓冲 |

每个 `Compress` 中间件还拥有自己的 gzip writer 池。池化减少分配和 GC 压力，但 `sync.Pool` 不保证取回同一对象，也不保证某条路径绝对零分配；正确性依赖归还前重置，而不是对象身份。

## 请求期解析

- URL query 在需要时最多解析一次；urlencoded body 解码不会顺带重复解析 query；
- 多 key query 只解码 handler 能绑定的名称，保留重复值和标准百分号解码语义；
- JSON body 使用池化缓冲，空 body 判定合并进解析步骤；
- 多参数 JSON 只验证一次合法性，并保留所需顶层成员的原始切片，避免反复解码整个 body；
- 表单 body 也使用池化缓冲，已知长度只在总限额内预增长。

## 路由匹配

- 静态路由按动词存入独立 map，原始路径 O(1) 直查，命中时不分配路径参数；
- 静态未命中才检查连续/尾部斜杠，归一化后再查一次静态 map；
- 动态路由进入按段组织的树，路径段是与原路径共享存储的子串；
- 段切片和路径参数 map 来自池；树内静态子节点优先，变量分支失败会回溯清理。

## 惰性装箱

handler 的原始返回值以 `reflect.Value` 暂存；只有中间件真正调 `c.Result()` 时才装箱成 `any` 并缓存。不读 `Result` 的请求不支付这次装箱成本。

## 诚实的取舍

与成熟框架的剩余差距来自**反射调用任意 handler 签名**的固有代价——这是"签名即 API"这一核心特性带来的取舍。GBL 的策略是降低反射之外的开销，而不是承诺消除反射。

## 自己做基准

在你的应用模块中运行：

```bash
go test -bench=. -benchmem -run=^$ ./...
```

可信对比请遵守：

- 两种实现处理完全相同的 payload、路由和中间件；
- 复用请求与 writer，避免把测试夹具分配算进业务成本；
- 先预热，再使用 `benchstat` 比较多次运行的中位数和分布；
- 同时记录 `ns/op`、`B/op`、`allocs/op`，不要只看吞吐；
- 并行基准使用共享引擎，并确认没有测试专用全局状态互相干扰。

性能数字依赖硬件、Go 版本和工作负载，请以你自己环境中的结果为准。
